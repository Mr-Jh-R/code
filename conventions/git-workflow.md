# 通用 Git 协作与版本管理规范

适用于人工开发和 AI 工具，约束基线确认、任务隔离、提交、整合与发布。采用项目已有的分支策略、评审和 CI 门禁；本规范不强制使用 Git Flow，也不要求某个固定分支名、服务器目录或发布工具。

项目将实际集成分支、门禁、文档入口和发布方式记录在已有项目约定中；没有入口时可使用 [项目工作流模板](project-workflow.template.md)。发布授权以用户指令和项目权限为准，采用本规范本身不授予推送、部署或清理权限。

## 1. 确认工作基线

开始编辑、测试、生成契约文档或发布前：

1. 核对工作目录、当前分支、HEAD、已暂存/未暂存/未跟踪内容、远端及现有 worktree。
2. 从项目约定识别集成分支和目标发布线。通常一条主线汇集完整开发成果；维护多个版本时，明确本任务所属的版本线及回合入方向。
3. 需要判断是否最新时，先更新相关远端引用，再检查提交关系和实际补丁。网络不可用时说明引用尚未刷新，不能声称基线最新。
4. 简短说明本次工作区、分支、起始 SHA 和未提交依赖。发现与上次交付基线不同，先查清差异。

分支名、提交时间、目录名、监听端口或服务健康都不能单独证明版本新旧。没有项目约定时，先盘点各分支与未提交内容，提出有证据的基线建议；只有存在影响本次工作且无法判断的分歧时才请求决策。

在旧 linked worktree 中找不到约定时，通过 `git worktree list` 定位主工作区并读取其规则和整合登记。读取规则不等于允许复制另一工作区的业务源码。

完成条件：本次改动的起点、依赖、目标分支及授权范围明确。

## 2. 选择工作区与处理依赖

| 情况 | 处理方式 |
| --- | --- |
| 继续同一功能 | 复用原任务分支与工作区，接手前确认原任务已停止写入 |
| 顺序开展的小改动 | 项目允许时沿用已确认工作区，先区分已有修改的归属 |
| 独立且需要并行的任务 | 从对应集成分支的明确 SHA 建立短期功能分支和独立工作区 |
| 依赖未完成功能 | 优先等待合入；必须提前接续时，用明确的 WIP 提交建立依赖并登记目标合入位置 |
| 紧急修复或维护旧版本 | 按项目指定版本线操作，记录与当前集成主线的差异和回合入责任 |

新对话本身不是创建分支或 worktree 的理由。一次任务也不必机械新建分支；按并行冲突、变更风险和项目策略决定隔离方式。

同一工作区同一时刻只安排一个写入任务；集成分支的合并、构建和发布串行执行。只读分析可以并行，读取中的内容有变动时重新确认事实。其他工作区未提交的文件不会通过 fetch、pull 或新建分支自动传入。

确有并行任务或待整合依赖时，在现有 issue、PR、OpenSpec change 或项目登记处记录：任务、分支/工作区、起始 SHA、依赖提交、改动范围、目标分支、状态及接手责任。单个小任务无需另建登记系统。

完成条件：每个写入任务有明确归属，未提交或未集成的依赖不会被误认为已进入主线。

## 3. 提交与整合

- 保留其他任务的已暂存、未暂存及未跟踪内容。同文件交叉修改时先核对归属，按差异合并；不通过整目录覆盖、重置或清理消除差异。
- 按任务的明确文件或补丁清单暂存并复核 diff，在授权范围内形成可追溯提交。混合工作区不使用全量暂存；已有他人暂存内容不能被顺带提交或取消暂存。仅要求只读检查或文档草稿时不自动提交。
- 遵循项目的 PR、评审及分支保护策略。共享历史不擅自重写；重整个人任务历史时也先确认依赖方和远端状态。
- 合入前同时检查提交关系和实际补丁。已手工移入、squash 或改写的功能，即使原 SHA 不在祖先链上，也不能重复 cherry-pick；已存在合并提交仍需验证实际行为。
- 合入后按累计改动范围运行集成检查；功能分支验证通过不代表完整基线已验证。合并后才发现的修复也要保留在集成提交中。
- 已授权的提交与整合继续执行，无需逐步再次确认。将覆盖他人改动或无法判断业务冲突时，先提供具体差异，再请求决策。

完成条件：提交范围可审查，整合目标和验证结果明确，未完成的整合有来源和责任人或任务。

## 4. 运行版本与文档基线

用源码 SHA、未提交实现、构建来源和运行实例共同确认版本。主开发文档默认对应已确认的集成开发基线；尚未集成的接口另标适用分支和状态。用户明确指定功能分支、工作区、提交或发布版本时，按指定目标核对并标注适用范围。

源码、契约定义、生成客户端和运行后端应对应同一基线。无法启动或取得同版本契约时，可继续源码审查并标注运行证据缺口；不能用其他工作区的旧实例补成“验证通过”。接口数量或路径覆盖不能替代字段、序列化和业务行为核对。

API 文档任务通过项目入口找到已安装的 `api-contract-docs` Skill；未安装时按项目已有契约核对流程完成，不假设固定语言、框架、端口或文档文件名。

## 5. 发布与回退（有发布任务时）

1. 固定已经验证的集成提交，说明功能范围、受影响组件和检查结果。独立紧急发布另记回合入责任。
2. 按项目策略使用不可变版本标识，如发布标签、完整 SHA 或制品摘要。使用标签时核对远端实际指向；重新发布修复版本使用新标识，不移动已发布标签。
3. 确认实际部署目标、构建来源、生效配置、持久化数据和当前运行版本。源码部署时检查服务器 Git 状态；镜像或制品部署时核对不可变摘要，不能只凭共享标签判断版本。
4. 保留回滚版本、制品与配置来源；同一部署目标的构建、更新、重启和回滚串行协调。日志和发布记录不保存秘密值。
5. 验证健康、运行版本及本次行为，再报告发布完成。应用回退不等于数据库迁移已回退，数据变更按独立兼容或恢复方案处理。

完成条件：能够回答“发布了哪个提交和制品、部署到哪里、如何验证、如何回退”。

## 6. 交付与清理

按适用范围分别报告：

- **已实现**：行为或文档变化，以及验证结果。
- **已提交**：提交 SHA、是否推送；未提交则说明原因。
- **已集成**：目标分支、集成 SHA 和累计验证结果；待整合则说明来源与责任。
- **已发布**：目标环境、版本/制品、运行验证和回滚点；没有发布任务时标为未发布或不适用。

OpenSpec 归档、代码提交、合入与发布是不同状态，不能相互替代。确认成果已保留、工作区没有待保留内容且无任务或服务依赖后，才在授权范围内整理分支和 worktree；未要求清理时只列出可归档项。
