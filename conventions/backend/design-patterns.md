# 设计模式与架构模式选型

> 设计模式是处理已存在复杂性和变化点的共享语言，不是代码质量目标。简单、直接、可测试的实现优先于预设扩展层。

## 一、引入门槛

引入模式前必须回答：

1. 当前已经出现的变化点、分支、耦合或失败风险是什么？
2. 为什么直接实现、提取函数或组合现有对象已经不够？
3. 模式隐藏了什么复杂性，调用方因此少知道什么？
4. 新增常见变体时，哪些文件不再需要修改？
5. 如何独立验证每个策略、状态、适配器或处理器？
6. 类、接口、消息和运行时成本是否低于维护收益？

引入后至少满足：

- 常见调用路径更短或更清晰。
- 依赖方向和所有权更明确。
- 变化局限在一个边界内。
- 失败语义、线程安全和生命周期没有被隐藏。
- 测试能直接覆盖模式承担的规则。

只为“以后可能用到”建立的接口、工厂、事件或抽象类应当删除。模式不再降低复杂度时，允许退回直接实现。

## 二、对象与流程模式

| 场景 | 可选模式 | 适用判断 | 主要风险 |
|---|---|---|---|
| 多种可替换业务规则或算法 | Strategy | 规则有独立变化原因，主流程不应随新增规则修改 | 每个微小分支都拆成类 |
| 对象构造复杂且存在真实变体 | Factory | 调用方不应知道实现类型或装配细节 | 工厂只包装一次构造调用 |
| 可选参数多且对象需要一次性保持合法 | Builder | 构造步骤可读性和不变量明显改善 | 为简单数据对象增加冗余 API |
| 外部 SDK、旧系统或协议接入 | Adapter | 需要隔离外部模型、异常和版本变化 | 只改名字段，没有真正隔离边界 |
| 在不改变核心对象时附加横切行为 | Decorator | 缓存、度量、审计等行为可独立组合 | 装饰顺序影响语义却未记录 |
| 多个步骤按顺序处理并可组合、短路 | Pipeline / Chain of Responsibility | 步骤边界稳定，顺序和终止条件明确 | 数据在处理器间隐式变形 |
| 行为随有限状态发生严格变化 | State / State Machine | 合法迁移和拒绝原因比普通分支更重要 | 状态分散在对象和数据库两套实现 |
| 一个事实需要通知多个独立消费者 | Domain Event / Observer | 发布者不应依赖消费者，接受明确一致性模型 | 用事件隐藏同步调用链或关键失败 |
| 主流程稳定，仅少量步骤变化 | Template Method | 步骤顺序是稳定不变量且继承收益明确 | 继承耦合、脆弱基类和隐式调用 |
| 复杂计算由可组合条件描述 | Specification / Policy | 条件需要组合、解释和独立测试 | 用对象图替代一个简单谓词 |

### 2.1 Strategy

- 策略接口表达一个稳定业务能力，不以技术动作命名。
- 策略选择逻辑集中在组合根、注册表或明确工厂中。
- 每个策略独立测试；默认策略和未知策略的行为明确。
- 策略需要共享大量可变状态时，先重新检查边界是否正确。

### 2.2 Factory 与 Builder

- Factory 负责选择和合法装配，不承载创建后的业务流程。
- Builder 在 `build` 时验证整体不变量，构建后对象尽可能不可变。
- 依赖注入容器已经能清晰完成固定装配时，不再增加同义工厂。

### 2.3 Adapter

- 核心接口使用领域语言，适配器完成外部 DTO、错误、认证和协议转换。
- 外部新增字段和异常不迫使领域层同步修改。
- 适配器测试覆盖超时、错误响应、非法结构和版本差异。

### 2.4 Decorator

- 装饰器保持被装饰接口的契约，不改变调用方未声明的语义。
- 顺序敏感的装饰器明确组合次序，例如“重试包裹度量”与“度量包裹重试”结果不同。
- 事务、缓存和重试等隐式装饰行为必须能从配置或代码入口发现。

### 2.5 Pipeline 与责任链

- 每个步骤声明输入、输出、副作用、是否可短路和失败处理。
- 顺序属于业务规则时由显式配置或组合代码固定，并测试关键排列。
- 不使用共享无类型上下文承载所有数据；稳定字段使用明确类型。

### 2.6 State Machine

- 使用单一来源定义状态、事件、守卫条件和副作用。
- 数据库更新携带预期状态或版本，防止并发越过合法迁移。
- 迟到异步结果携带 version、generation 或 fencing token。
- 测试覆盖所有合法迁移、非法迁移和重复事件。

### 2.7 Domain Event

- 事件使用过去式命名，表达已经发生的事实，不表达远程命令伪装的通知。
- 事件 schema 包含版本、发生时间、聚合标识和幂等标识。
- 同步进程内事件不伪装成可靠消息；要求可靠投递时使用 outbox。
- 需要消费者成功才能提交主业务时，优先显式同步编排，不使用无反馈广播。

## 三、边界与数据模式

| 场景 | 可选模式 | 适用判断 | 主要风险 |
|---|---|---|---|
| 隔离领域与持久化技术 | Repository | 聚合需要稳定的数据访问契约 | 每张表机械创建 CRUD Repository |
| 一个用例协调多个持久化操作 | Unit of Work / Transaction Script | 需要一个明确提交边界 | 把长远程调用包含在事务中 |
| 读写模型差异显著 | CQRS | 两侧有不同扩展、权限或模型需求 | 为普通 CRUD 引入双模型和同步成本 |
| 保存业务数据并可靠发布事件 | Transactional Outbox | 数据与事件必须原子提交 | 没有 relay、重试、清理和幂等消费 |
| 消费消息并防止重复副作用 | Inbox / Idempotent Consumer | 消息至少一次投递 | 去重记录无保留期或键选择错误 |
| 读取密集且允许受控陈旧 | Cache-Aside | 缓存失效和一致性窗口可定义 | 无界 key、缓存穿透和陈旧权限数据 |

### 3.1 Repository

- Repository 围绕聚合或一致性边界命名，不围绕表生成完整 CRUD 表面。
- 查询返回领域需要的对象或投影，不泄漏驱动、ORM 或数据库行类型。
- 事务所有权属于应用用例，Repository 不在调用方不知情时任意提交。
- 复杂查询可以使用专用查询对象或 read model，不强迫聚合承担报表职责。

### 3.2 CQRS

只有以下条件同时成立时才考虑 CQRS：

- 读写模型确实有不同的结构、吞吐、权限或部署需求。
- 团队能承担投影同步、最终一致性、回放和故障恢复。
- 简单查询投影或独立查询服务不能解决问题。

CQRS 不等于必须使用事件溯源，也不等于每个命令和查询都创建独立类。

### 3.3 Outbox 与 Inbox

- Outbox 与业务变更在同一事务写入，relay 使用租约或竞争安全的 claim。
- 发布携带稳定 event ID，消费者按该 ID 或业务幂等键去重。
- 定义重试、死信、监控、保留期和归档，不能只创建一张 outbox 表。
- Inbox 去重和业务副作用必须在同一事务或等价原子边界内完成。

## 四、分布式可靠性模式

| 场景 | 可选模式 | 核心要求 |
|---|---|---|
| 瞬时依赖失败 | Retry with Backoff | 幂等、有限次数、指数退避、抖动和总预算 |
| 持续依赖失败 | Circuit Breaker | 按依赖隔离、半开探测、可观察状态 |
| 保护稀缺下游资源 | Bulkhead | 并发、连接、线程或队列独立限额 |
| 跨服务长业务流程 | Saga / Compensation | 每步幂等、补偿语义和人工恢复 |
| 多实例任务所有权 | Lease + Fencing Token | 过期所有者不能提交新结果 |
| 重复请求或回调 | Idempotency Key | 作用域、请求指纹、结果复用和保留期 |
| 逐步替换旧系统 | Strangler Fig | 明确路由、数据所有权和退场条件 |

### 4.1 Retry

- 只重试明确瞬时错误，不重试校验、权限和确定性业务失败。
- 写操作必须幂等或具备幂等键。
- 重试集中在一个责任层，避免多层乘法放大。
- 总 deadline 覆盖所有尝试和退避时间，并暴露尝试次数指标。

### 4.2 Circuit Breaker 与 Bulkhead

- Circuit Breaker 防止持续调用已知故障依赖，不能替代超时。
- Bulkhead 限制故障和排队范围，不能使用一个全局池耦合无关依赖。
- 降级结果必须满足业务安全，不能把未知状态伪装为成功。

### 4.3 Saga

- 每一步定义正向动作、幂等键、可补偿性和不可逆边界。
- 补偿是新的业务动作，不是假设时间可以回滚。
- 编排式 Saga 适合需要集中可见流程；协同式事件适合边界清晰且链路短的流程。
- 失败流程有可查询状态、重试上限和人工干预入口。

### 4.4 Lease 与 Fencing Token

- lease 只表达限时所有权，持有者必须续租并检测丢失。
- 每次获得 lease 生成单调递增 token，下游写入拒绝旧 token。
- 仅检查“租约当时未过期”无法防止暂停后的旧 worker 覆盖新结果。

## 五、常见反模式

- **接口镜像**：每个具体类都配一个没有替换价值的同名接口。
- **贫血转发层**：Controller、Service、Manager、Repository 多层只传递相同参数。
- **万能上下文**：使用无类型 Map 在处理器间传递不断增长的隐式状态。
- **公共垃圾层**：把无关逻辑放入 `Common`、`Base`、`Helper` 或全局工具类。
- **事件化逃避**：用事件隐藏本应显式处理的同步依赖、事务和错误反馈。
- **继承复用**：为复用少量代码建立脆弱基类和受保护可变状态。
- **模式先行**：从模式名称出发寻找使用场景，而不是从已存在复杂性出发。
- **分布式单体**：服务拆开但共享数据库、同步链路和发布节奏，失败反而扩散。
- **本地正确幻觉**：使用进程锁、内存队列或本地 semaphore 声称多实例安全。
- **抽象泄漏**：调用方仍需理解适配器内部协议、重试或存储细节才能正确使用。

## 六、设计记录模板

对影响模块边界、数据所有权、分布式一致性或长期扩展方式的模式选择，记录以下内容：

```markdown
# 决策：<名称>

## 背景
当前复杂性、变化点、约束和失败风险。

## 决策
选择的模式、边界、接口和所有权。

## 替代方案
直接实现及其他模式为什么不适用。

## 后果
获得的收益、新增成本、运行时风险和退出条件。

## 验证
测试、指标、故障演练或架构检查如何证明决策有效。
```

模式选择没有形成长期架构影响时，可以在代码评审或设计文档中简短记录，无需为每个局部策略创建 ADR。
