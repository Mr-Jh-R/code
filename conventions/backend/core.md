## 一、规则级别与核心原则

本文使用以下关键词：

- **必须**：关系到契约、安全、数据一致性、并发正确性或生产可运维性，评审不得无理由放行。
- **应当**：默认采用；偏离时在代码、设计文档或评审记录中说明原因和替代保障。
- **可以**：按项目规模和场景选择。

所有后端变更遵守以下原则：

1. **契约清晰**：协议语义、业务语义和实现细节分离，对外行为可由文档和测试验证。
2. **默认安全**：认证、授权、敏感信息和内部接口在配置错误时仍然失败关闭。
3. **不变量下沉**：核心不变量由最接近数据和状态的一层保证，不只依赖调用方自律。
4. **边界隔离**：第三方协议、数据库结构和框架类型停留在适配层。
5. **有界资源**：线程、连接、队列、任务和下游调用有所有者、容量、超时与关闭路径。
6. **失败可恢复**：区分永久、瞬时和未知错误，具备幂等、补偿或人工处置路径。
7. **生产可观察**：日志、指标、追踪和审计能从用户影响定位到依赖或状态迁移。
8. **渐进演进**：先修正高风险行为，再改善结构；不借需求进行无关的全仓重写。
9. **深模块**：抽象隐藏复杂性、缩小接口或隔离真实变化点，纯转发层不构成设计价值。

## 二、模块与依赖

### 2.1 业务边界

- 顶层模块优先按业务能力划分；模块内部再按接口、应用、领域、持久化和外部适配组织。
- 每个模块定义所有权、公开接口和持久化边界，只暴露调用方需要的最小能力。
- 跨模块调用通过公开应用接口、事件或稳定协议完成，不直接访问其他模块的内部存储。
- 依赖方向由构建边界、可见性或架构测试验证。循环依赖视为边界问题，不用全局容器掩盖。
- 分布式服务边界还必须明确数据所有权、兼容策略、超时预算和故障传播方式。

### 2.2 参考职责

名称可以随技术栈变化，职责不得混淆：

| 角色 | 负责 | 不负责 |
|---|---|---|
| 传输适配层 | 路由、认证上下文、输入解码、结构校验、协议状态和响应头 | 核心业务编排、持久化细节、吞掉通用异常 |
| 应用层 | 用例编排、事务边界、幂等和授权后的业务动作 | HTTP/消息框架对象、供应商模型、动态查询拼接 |
| 领域/策略层 | 业务计算、状态迁移和核心不变量 | 网络、数据库驱动和传输协议 |
| 持久化适配层 | 查询、映射、约束配合和持久化并发控制 | 对外响应、远程调用、跨边界工作流 |
| 外部系统适配层 | 协议、认证、超时、错误翻译和响应校验 | 核心业务状态迁移 |

复杂状态机必须集中表达允许的迁移、前置条件和拒绝原因。调用方不得复制条件判断形成不同版本的状态规则。

### 2.3 接口和抽象

- 存在多个真实实现、稳定跨模块端口、外部系统适配或明确测试替身价值时，应当定义接口。
- 单一、简单且不跨边界的实现可以直接使用具体类型，不机械创建一一对应的接口和实现类。
- 接口按业务能力命名；实现按策略、存储或供应商命名。
- `Common`、`Base`、`Helper`、`Utils` 不承载无关职责。共享代码必须有清晰所有者和稳定语义。
- 新增抽象后，常见调用应更简单，变化应局限在边界内，并能独立测试；否则保留直接实现。
- 设计或重构复杂模块时，同时遵守 [`design-patterns.md`](design-patterns.md)。

## 三、实现与可维护性

### 3.1 命名和类型

- 遵循语言生态中可自动执行的格式和命名规范；项目画像只记录偏离点。
- 名称表达业务含义、方向和单位，例如 `leaseExpiresAt`、`timeoutMillis`。
- 核心语义不使用含糊的 `data`、`info`、`flag`、`process`。
- 方法或函数保持一个抽象层级，名称表达意图而不是实现步骤。
- 参数共同描述一个概念且频繁成组出现时，使用参数对象或值对象。
- 不使用布尔参数承载不同业务路径；改用有语义的方法、命令或策略。
- API 模型、持久化模型、领域对象和外部系统模型保持职责分离。
- 空值、缺失值和错误使用语言生态的明确表达，不以魔法字符串或特殊数字传递。

### 3.2 依赖和副作用

- 依赖显式传入并尽可能不可变，避免隐藏的全局依赖和服务定位器。
- 业务计算与 I/O 分离；副作用集中在少量明确边界，便于测试和失败恢复。
- 使用卫语句拒绝非法输入和状态，拒绝原因稳定且可诊断。
- 时间、随机数、ID 和环境依赖在需要确定性测试时通过可替换端口注入。
- 共享可变状态必须说明所有者和同步策略，局部不可变值优先。
- 连接、文件、流、锁和任务使用结构化生命周期，在成功、失败和取消时均释放。
- 动态代码执行、反射或元编程只在收益明确且有测试覆盖时使用。
- 提交中不保留调试输出、注释掉的旧实现、失效注释和无理由的检查忽略。

### 3.3 注释和文档

- 稳定公共契约、跨模块接口以及涉及幂等、线程安全、单位、副作用或特殊边界的方法必须有契约说明。
- 自解释的访问器、简单转发和私有实现不强制文档注释。
- 注释解释原因、约束和风险，不逐行翻译实现。
- API、事件和数据格式的权威定义放在机器可验证的契约中，说明文档通过指针引用。
- 作者、时间和修改历史由版本控制提供。

### 3.4 模型边界

- 持久化实体、输入 DTO、输出 VO/视图模型、领域对象和外部系统模型保持职责分离；不因字段相似而共享同一公开类型。
- 稳定或复杂的输入契约使用显式请求模型；简单路径标识、文件流和框架上下文可以作为独立参数，不为了形式全部包装成 DTO。
- 公共 API 默认返回稳定的输出模型，不直接暴露持久化实体、内部状态、凭证、逻辑删除字段或供应商对象。
- Java/Spring 项目可以按 `model/dto/<domain>`、`model/entity/<domain>`、`model/enums/<domain>`、`model/vo/<domain>` 组织；模块化项目也可以把模型放在所属业务模块内。目录名按项目现有边界决定，不为套用模板移动代码。
- 请求模型使用“资源/领域 + 意图 + Request”等能表达业务语义的名称；新增、查询、登录和领域动作不强制使用同一 CRUD 词汇。
- 只有请求仅表达单个通用 ID 时才复用公共删除/分页模型；批量、复合条件、资源专属字段、版本校验和不同分页语义使用专用模型。

## 四、API 与协议

### 4.1 通用规则

- 对外契约使用适合协议的机器可读描述，例如 OpenAPI、AsyncAPI、Protocol Buffers 或 JSON Schema。
- 契约说明输入、输出、认证、错误、幂等、排序、分页、版本和兼容策略。
- 写操作必须定义幂等性，客户端、网关或消费者重试不得产生无法识别的重复副作用。
- 外部提供的资源、租户和操作者标识均视为不可信，必须结合认证上下文授权。
- 新字段优先向后兼容；删除、重命名、收紧校验和改变默认值按破坏性变更管理。
- 时间、时区、金额、精度、编码、枚举未知值和大小单位必须明确。

### 4.2 HTTP

- URI 围绕资源建模。非 CRUD 动作可以使用命令端点，但必须说明状态迁移和幂等性。
- 查询使用 `GET`，创建使用 `POST`，整体替换使用 `PUT`，局部修改使用 `PATCH`，删除使用 `DELETE`。
- 创建成功返回 `201 Created` 和 `Location`；异步受理返回 `202 Accepted` 和任务地址；无响应体返回 `204 No Content`。
- 输入错误、认证失败、禁止访问、不存在、冲突、限流和服务端错误使用真实 HTTP 状态，不统一返回 `200`。
- 并发更新使用版本字段或 `ETag`/`If-Match`；冲突返回 `409 Conflict`，前置条件失败可以返回 `412 Precondition Failed`。
- 文件、流式响应、SSE 和 WebSocket 按各自协议建模，不强行包装普通 JSON。

### 4.3 输入校验

- 传输适配层执行结构、类型、格式、长度和范围校验；跨字段、持久化状态和权限校验位于应用或领域层。
- 优先使用声明式校验和统一错误转换，避免在每个入口复制检查。
- 文件上传校验服务端大小、扩展名、媒体类型、文件签名和解析复杂度；客户端文件名不直接作为存储路径。
- 分页限定最大页大小并使用服务端排序白名单。大数据集使用稳定排序的 cursor/keyset 分页。
- 稳定契约使用显式模型，不使用无结构字典或动态对象承载固定字段。

## 五、错误处理

### 5.1 两层语义

业务错误码可以保留，但不能替代协议状态：

```text
协议状态   -> 供网关、监控、缓存、重试框架和通用客户端判断
业务错误码 -> 供业务分支、用户提示、统计和排障使用
requestId  -> 关联客户端响应、日志和 trace
```

- 一个业务码稳定映射到同类协议状态，不能为了方便全部映射为“参数错误”或“操作失败”。
- 业务错误定义集中管理，业务代码不构造未登记的裸数字或临时字符串错误码。
- 错误响应至少包含机器可识别的 `code` 和安全的 `message`。
- 统一中间件将 request/trace ID 写入响应头，并建议在错误体同步返回。
- 字段校验错误使用结构化详情，不包含堆栈、查询、路径、供应商原文或令牌。
- 项目可以采用 RFC 9457，也可以采用统一业务错误体；选择写入项目画像并通过契约测试固定。

### 5.2 HTTP 参考映射

| 场景 | HTTP | 业务码示例 |
|---|---:|---|
| 请求解析或字段校验失败 | 400 | `INVALID_ARGUMENT` |
| 凭证缺失或无效 | 401 | `UNAUTHENTICATED` |
| 无权执行 | 403 | `PERMISSION_DENIED` |
| 资源不存在或不可见 | 404 | `NOT_FOUND` |
| 版本、状态或唯一性冲突 | 409 | `CONFLICT` |
| 请求体超过限制 | 413 | `PAYLOAD_TOO_LARGE` |
| 请求频率或配额超限 | 429 | `RATE_LIMITED` |
| 未预期服务端错误 | 500 | `INTERNAL_ERROR` |
| 上游响应无效 | 502 | `UPSTREAM_ERROR` |
| 服务暂时不可用 | 503 | `UNAVAILABLE` |
| 上游超过总时限 | 504 | `UPSTREAM_TIMEOUT` |

业务码可以采用数字、字符串或分段编码，但必须唯一、稳定、可检索，并与协议状态解耦。

### 5.3 全局错误边界

- 在协议最外层设置统一错误边界，集中完成状态映射、响应脱敏、关联 ID 和日志分级。
- 入口代码不捕获所有异常后返回异常原文。已知失败转换为登记的业务错误，其余交给全局边界。
- 解析、校验、方法不支持、媒体类型、上传超限和冲突分别映射。
- 预期 4xx 通常记录低级别结构化事件；未知 5xx 在责任边界记录一次完整堆栈。
- 同一异常不在外部适配、应用层、传输层和全局边界重复记录完整堆栈。
- 客户端消息来自安全模板或明确允许的上下文；原异常作为内部 cause 保留。
- 契约测试同时断言协议状态、业务码、响应结构和敏感信息未泄漏。

## 六、安全与隐私

### 6.1 默认拒绝

- 所有非公开入口必须认证，授权采用默认拒绝。公开入口通过显式白名单管理。
- 鉴权、密钥或关键安全配置无效时，生产服务启动失败或拒绝流量。
- 内部接口同样需要服务身份、时效和防重放机制，不能只依赖内网地址。
- 操作者、租户、用户和角色来自已验证的认证上下文。
- 资源查询和写入带入主体或租户范围，防止只凭资源 ID 跨边界访问。
- 高风险操作执行对象级和动作级授权，并留下独立审计记录。

### 6.2 凭证和会话

- 密钥、密码、令牌和私钥通过受控配置或密钥管理系统提供，源码和公共默认配置不包含可用凭证。
- 凭证进入版本控制后先吊销和轮换，再清理历史。
- 日志、异常、指标和审计不记录密码、令牌、私钥或完整签名 URL。
- 令牌校验限定算法、签发方、受众、有效期和生效时间，并支持密钥轮换。
- 浏览器会话正确设置安全 Cookie 属性，并根据认证模式防护 CSRF。

### 6.3 输入、网络和滥用

- 登录和找回接口具备账号级、来源级限流和渐进延迟或锁定，响应不泄漏账号是否存在。
- 高成本接口设置请求大小、并发、频率、租户配额、成本预算和总时限。
- 服务端访问用户提供的 URL 时限制协议、主机、端口、解析 IP、重定向和响应大小，防护 SSRF 与 DNS rebinding。
- 查询、命令、模板、路径和日志使用结构化或参数化 API，动态标识符只来自服务端白名单。
- 服务和数据账号遵循最小权限；调试入口、管理接口和 API 文档在生产关闭或强认证。
- 发布流程包含依赖、镜像和基础设施漏洞扫描，例外有责任人和到期时间。

### 6.4 数据生命周期

- 敏感数据定义用途、访问角色、保留期、删除路径、导出方式和审计策略。
- 收集和传输遵循数据最小化；测试、日志和分析使用脱敏或合成数据。
- 加密覆盖传输和适用的静态存储，密钥与数据分离并支持轮换。
- 删除覆盖主库、搜索索引、对象存储、缓存和依法允许删除的派生数据。
- 数据分级、跨区域传输和供应商处理范围记录在项目画像或合规文档。

## 七、事务与一致性

- 事务位于具体用例的应用入口，范围小而明确。
- 框架通过代理、装饰器或拦截器提供事务时，必须理解自调用、异步和线程切换的影响。
- 数据库事务中不执行耗时文件解析、远程调用、模型推理、连接关闭或不可控回调。
- “业务提交 + 可靠发送事件”使用事务 outbox、日志型消息或等价原子方案。
- 失败状态需要在主事务回滚后保留时，通过独立事务或外部状态机记录。
- 乐观并发更新携带版本或预期状态，并检查实际更新数量；失败转换为冲突错误。
- 跨系统操作明确幂等键、重试边界、补偿和人工恢复路径。
- 事务、查询和锁等待设置总时限；死锁、序列化失败和唯一冲突按数据库语义分类。
- 分布式事务只在业务一致性确实要求且运维能力匹配时采用，默认优先本地事务、幂等事件和补偿。

## 八、并发与异步

### 8.1 锁和共享状态

- 锁只保护最小内存状态迁移。网络、数据库、文件、等待、连接关闭和可能回调的操作在锁外执行。
- 明确锁顺序，避免嵌套锁；状态机使用 version、generation 或 fencing token 拒绝迟到结果。
- 共享状态说明所有者、可见性、同步策略和生命周期。
- 关键状态只在进程内时，明确接受重启丢失和单实例限制，或提供恢复与路由机制。
- 多实例限流、租约、锁和配额使用共享协调存储或下游网关实现，不只依赖单进程原语。

### 8.2 执行器和任务

- 执行器、调度器和长生命周期任务由运行时或容器统一创建、命名、观测和关闭。
- 队列有界并定义拒绝策略，容量根据下游吞吐和可接受等待时间估算。
- 轻量线程、协程或异步 I/O 不提高数据库、GPU、外部 API 或内存容量，仍需 bulkhead 和配额。
- 定时任务和 worker 幂等，使用 lease、heartbeat 和 fencing token 防止旧 worker 提交结果。
- 异步任务传递 request/trace ID、租户和必要安全上下文，并支持取消或总 deadline。
- 应用关闭时停止接收新任务，等待有界时间，保存或转移可恢复工作，最后释放资源。
- 测试和服务关闭后不遗留任务或非预期线程。

## 九、外部系统与消息

### 9.1 外部调用

- 每个外部系统通过专用适配器隔离，供应商模型、异常和状态码不进入核心业务。
- 设置连接、响应和请求总 deadline，以及最大响应体、连接池和并发上限。
- 重试使用指数退避、抖动和总预算，只覆盖明确的瞬时错误与幂等请求。
- 熔断、限流和并发隔离按依赖或端点维度统计。
- 响应在使用前校验协议状态、媒体类型、大小、结构、枚举、范围和关联标识。
- 依赖失败保留可诊断 cause，对调用方返回项目定义的安全错误。

### 9.2 消息和事件

- 事件定义所有者、schema、顺序键、幂等标识、版本策略和敏感字段。
- 消费者按至少一次投递设计，重复消息不重复产生副作用。
- 重试分为短暂、延迟和死信/人工处置，并有最大次数和可观察状态。
- 消息确认在业务提交后执行；需要原子性时使用 inbox/outbox 或等价模式。
- 事件演进保持向后兼容，消费者容忍未知字段。
- 要求可靠投递的事件使用持久消息；内存队列只承载允许重启丢失的事件。

### 9.3 实时连接

- WebSocket、流和设备连接绑定连接代次或会话版本，旧连接回调不能修改新会话。
- 心跳、空闲超时、重连退避、最大连接数、单连接缓冲和慢消费者策略必须明确。
- 连接关闭和回调不在持有业务锁时执行，断线恢复语义由协议定义并测试。

## 十、数据与持久化

### 10.1 所有权和访问层

- 一个写模型有明确所有者，其他模块通过公开接口或事件访问。
- 持久化适配器围绕聚合或一致性边界提供高内聚操作，不汇总成整个 schema 的工具类。
- 查询参数化；动态列、排序、表名和表达式只来自服务端白名单。
- 映射集中复用，查询只选择需要字段；批处理使用数据库或驱动的批量能力。
- 数据库异常转换为稳定错误，同时保留原始 cause。

### 10.2 Schema 和迁移

- 表或集合有稳定主键；必填、唯一、引用、范围、非负计数和合法状态使用存储原生约束表达。
- 外键、引用和级联行为明确，并根据查询和父记录变更评估引用列索引。
- 跨租户和归属关系使用复合键或等价约束，存储层不能把 A 的子资源绑定到 B。
- 时间使用明确时区语义；持续时间、大小、金额和精度写明单位。
- 半结构化字段用于确实变化的数据，频繁过滤、关联和约束的字段正规化。
- 所有 schema 变更通过版本化迁移交付，已经在共享环境执行的迁移不可修改。
- 迁移默认 fail fast；幂等创建不得静默接受同名但定义不同的对象。
- 大表变更使用 expand-migrate-contract，并评估存量数据、锁定时间、失败恢复和新旧版本兼容窗口。
- 回填可断点、可观测、限速并验证结果。

### 10.3 查询和容量

- 索引由真实查询和数据分布驱动，核心查询使用目标数据库的执行计划工具验证。
- 复合索引匹配过滤、关联和排序，同时考虑写放大和存储成本。
- 向量、全文、空间、JSON 和部分索引记录目标查询、选择率和准确率/延迟取舍。
- 连接池结合数据库连接预算、实例数和查询时长配置，并监控等待和耗尽。
- 深分页使用 cursor/keyset；批量读取、导出和聚合设置上限或流式处理。
- 缓存定义 key 所有权、TTL、容量、一致性、击穿防护和失效策略。

数据库特有行为由项目画像选择对应附录，不将一个数据库的经验规则套用到另一个数据库。

## 十一、可观测性与运维

- 每个请求、消息、异步任务和外部调用携带 request/trace ID，并通过结构化日志关联。
- 日志记录事件、稳定标识、状态、耗时和结果；敏感正文和高基数字段不进入指标标签。
- 至少观测流量、错误、延迟和饱和度，并覆盖队列、连接池、worker lease 和外部依赖。
- liveness 只表示进程存活；readiness 表示能否接收流量。
- 关键业务操作使用独立审计，包含可信操作者、对象、动作、结果、版本和时间。
- 告警围绕用户影响、SLO 和可执行处置，不以单条异常日志作为默认条件。
- 发布具备健康探测、渐进放量、快速停止和兼容回退能力。
- 备份、恢复、灾难切换和数据删除流程定期演练，不能只验证备份任务成功。

## 十二、配置与供应链

- 公共配置只保存非敏感且各环境安全的默认值，生产必填配置缺失时启动失败。
- 配置使用类型化绑定和启动校验；超时、并发、队列、大小和速率带单位与合法范围。
- 环境差异来自配置而非代码分支，本地、测试和生产的安全边界明确。
- 依赖版本由锁文件、依赖清单或平台约束固定，自动升级经过测试和兼容验证。
- 构建产物可复现并生成 SBOM，发布物来源、签名和部署版本可追溯。
- 依赖、镜像和构建插件执行漏洞与许可证检查，例外有责任人和到期时间。
- 生产关闭或强认证调试端点、详细错误页、管理界面和交互式 API 文档。

## 十三、测试与质量门禁

### 13.1 测试策略

- 业务规则、状态机、错误映射和纯转换使用快速单元测试。
- API/协议测试断言认证、校验、状态、业务码、序列化和兼容契约。
- 持久化和迁移使用与生产数据库版本、扩展和语义足够接近的环境。
- 外部适配器使用契约测试覆盖超时、非成功状态、非法响应、响应过大和重试边界。
- 消费者测试重复、乱序、延迟、毒消息和重放。
- 并发测试使用屏障、可注入时钟和受控调度，不依赖睡眠猜测时序。
- 安全测试覆盖未认证、越权、对象级授权、注入、SSRF、上传、限流和敏感响应。
- 缺陷修复先增加可稳定复现的测试，确认修复前失败、修复后通过。

### 13.2 自动化门禁

项目的标准验证命令或 CI 应统一执行：

1. 格式化、lint、类型检查和依赖边界检查。
2. 编译、单元测试和适用的集成测试。
3. 静态分析，按风险和误报率分阶段启用。
4. 依赖、镜像、密钥和许可证扫描。
5. 覆盖率趋势和变更覆盖，关注关键分支而非单一百分比。
6. API/schema 兼容、数据库迁移和架构验证。
7. 按风险执行性能、安全和故障注入测试。

首次引入工具时，将机械格式化与业务变更分开。忽略检查必须局部、可检索并说明原因。

### 13.3 评审顺序

评审依次关注：正确性与安全、契约与兼容、数据与并发、可运维性、测试、设计复杂度、风格。格式问题交给工具处理，不占用主要人工评审精力。

## 十四、完成标准

后端变更完成前逐项确认：

- **契约**：协议状态、业务码、校验、认证、授权、幂等和版本一致。
- **数据**：事务、冲突、约束、迁移兼容、查询计划、容量和恢复路径已覆盖。
- **并发**：锁内只有受控操作；任务、队列、连接和共享状态有所有者、上限和关闭路径。
- **依赖**：外部调用有总 deadline、响应校验、限流、幂等重试和失败观测。
- **安全隐私**：没有引入凭证、越权、敏感日志、注入、SSRF、上传或数据生命周期风险。
- **运维**：关联 ID、指标、健康状态、审计和故障信息足以支持生产处置。
- **测试**：运行与风险匹配的验证，并报告结果、跳过项和剩余风险。
- **范围**：提交只包含目标所需变更，迁移和兼容步骤已记录。
