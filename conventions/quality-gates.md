# 通用规范检查与质量门禁

适用于人工和各种 AI 编程工具。实现前读取适用规范，实现后单独核对差异；检查范围随风险变化。执行命令沿用项目已有构建、lint、测试和 CI，不要求统一语言、安装 hook 或引入新的检查系统。

普通任务在现有开发流程内轻量核对；用户要求规范专项审查或项目明确规定时，可调用已安装的 `standards-check` Skill。调用过该 Skill 的有效结果可以复用，不再额外重复一轮相同检查。具体命令和门禁填写到已有项目约定或 [项目工作流模板](project-workflow.template.md)，无需另建配置文件。

## 1. 按范围和风险选择检查

| 变更 | 默认检查范围 |
| --- | --- |
| 文案、注释、格式 | 相关格式、语法、链接和差异核对，不要求无关业务构建 |
| 普通功能或局部修复 | 受影响模块的 lint、类型/编译、相关测试，以及一次针对性规范审查 |
| 权限、事务、并发、数据库、公共接口、跨模块变更 | 在相关基础检查外补契约、集成或架构验证；按风险与项目约定选择独立审查 |
| 合并、打发布标签或发布 | 核对目标提交的必需检查、集成结果和发布制品来源；已有有效结果无需机械重跑 |

分类取决于影响，不只看扩展名或行数。修改脚本、CI、配置、规范的强制语义或示例命令时，还要核对执行影响。独立审查阶段不等于必须启动子代理；默认由主 Agent 串行完成，其他审查者按授权和项目需要加入。

## 2. 确认输入与适用规则

1. 明确检查的是工作区修改、某次提交、相对指定基线的变更，还是用户指定的全项目范围。核对分支、HEAD 与基线 SHA；不能默认把当前目录当成完整集成版本。
2. 工作区检查包含已暂存、未暂存及属于本任务的未跟踪文件；提交检查以目标提交内容为准。差异只是入口，涉及的调用方、配置和契约也要读。混合任务按归属划定范围，保留其他任务内容。
3. 从项目入口找到当前活动规范与项目例外，仅加载相关技术附录。没有依据的个人偏好不能作为规范违规；规则冲突按项目优先级裁决，无法裁决时报告具体冲突。
4. 选出本次必需检查和可选检查。已有命令从脚本、构建或 CI 中确认，不能虚构。未配置的能力如实说明，不能归为“不适用”。

完成条件：检查对象、基线、规则来源、必要上下文和必需检查项明确；已有信息足够时直接继续。

## 3. 自动检查与语义审查分工

| 规则类别 | 自动化适合检查 | 还需审查的内容 |
| --- | --- | --- |
| 格式、导入、命名 | formatter、lint、编译器、语法/类型分析 | 同名类型、框架配置等例外，不能只用正则判断全限定名 |
| 分层与依赖 | 依赖分析、架构测试 | 模块所有权、接口是否泄漏实现、是否过度封装 |
| 契约、事务与数据 | 契约测试、数据库集成测试 | 业务授权、状态迁移、事务范围和回滚含义 |
| 前端组件 | 类型、lint、组件/交互测试 | 是否已有组件可复用，公共组件是否有稳定语义 |
| 安全与发布 | 项目扫描、构建及 CI 校验 | 目标版本、敏感数据边界、迁移和回退证据 |

先运行可确定判断的检查，再单独阅读本次差异和相关上下文，核对自动检查没有覆盖的适用规则。编译成功、测试通过、OpenSpec 校验通过或 AI 没发现问题，都不能单独证明全部规范符合。

优先使用 check/只读模式。审查任务不运行格式化写回、业务写接口、部署或会修改共享数据的测试；确需执行有副作用的验证时先确认它已在授权范围内。正常构建缓存、测试临时产物按项目目录与隔离规则管理。

完成条件：自动检查有实际结果，语义问题有规则依据和代码证据，未覆盖部分明确。

## 4. 结果、修复与复查

检查状态统一区分：**通过、失败、执行异常、未执行、不适用**。执行异常包括工具缺失、超时和环境故障；不适用需说明与本次范围无关的原因。告警是否阻断由适用规则与项目门禁决定，不能把建议都升级为阻断。

- 问题分为确定违规、待确认和改进建议。每项给出规范路径/章节、代码位置、影响及修复方向；不能仅凭外观猜测业务缺陷。
- 默认只读；任务已经授权修复时，针对范围内问题修改并复查。检查器不擅自降低规则、删测试或扩大忽略范围以获得通过。
- 修复后重新执行受影响检查；变更触及公共配置、依赖或跨模块行为时扩大范围。无关且仍有效的检查结果可以复用。
- 复用结果须核对源码内容、相关未提交差异、检查命令/规则配置、依赖和环境未发生影响结果的变化；记录命令、范围、结果与对应 SHA 或工作区差异。只有旧对话中的“通过”不构成证据。
- 新失败或无法消除的不确定性应报告；同一问题反复修复仍无进展时停止盲目重试，说明证据和阻塞条件，不无限启动 AI 审查。
- 无关历史问题单独报告，不顺带全仓重构。项目允许的例外要有范围、理由、替代保障及责任/复审条件，不能由检查者默认为已批准。

完成条件：适用必需项通过，或存在项目政策明确允许且有权确认的例外；失败、执行异常和未执行都不能冒充通过。必需项未满足时，不宣布验收通过、不合并到受保护集成线或发布；可以如实保存符合项目策略的 WIP 提交。

## 5. 交付证据与触发位置

默认在对话、PR 或现有任务记录中简述：检查对象/基线、执行命令与状态、问题及限制。没有问题时说明“本次范围未发现违规”，不承诺零缺陷。用户未要求且项目无约定时，不新建检查报告文件。

- 编辑过程使用低成本的格式、语法和类型反馈；一个完整改动实现后做主要检查。不要每次小编辑都触发全量构建和 AI 审查。
- 手动命令和 CI 调用同一组项目检查；可选 Git `pre-push` 或 AI hook 仅负责触发和反馈，不另存一套规则。失败反馈要可定位，避免检查命令再次触发自身或无上限续跑。
- 本地 hook 可能未安装、被禁用或跳过，AI hook 的事件与阻断语义也依工具而异。命令不可用、超时或缺少证据时反馈真实状态，不能默认标绿。
- CI 在推送后失败不自动撤销推送，也不天然阻止打标签或部署。强制门禁需在使用方平台配置必需状态检查、分支保护和发布前置条件，限制绕过路径；不支持时明确由谁核对与放行。
- 合并后的代码需要匹配累计改动的验证；打发布标签或发布时核对目标 SHA/制品与证据一致。平台未配置门禁时只能报告已检查，不能声称已强制拦截。

本规范定义检查流程，不自动安装任何 hook、修改平台保护规则或赋予发布权限。
