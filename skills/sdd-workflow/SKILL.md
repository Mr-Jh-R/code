# SDD 工作流

用 OpenSpec 保存“做什么、为什么和进度”，用当前工具完成探索、实现、调试、审查和验证。能力名称可以不同，产出物和完成标准保持一致。

## 开始前

1. 读取项目入口文件，例如 `AGENTS.md`、`CLAUDE.md`、README 和目标目录附近的约束。
2. 根据项目入口完整读取本次任务适用的规范、项目画像和技术附录，不自行猜测路径或技术栈。
3. 检查 `openspec/`、现有 change、当前分支、工作区状态和权威验证命令。
4. 从构建文件、lockfile、workspace 和运行配置识别实际版本，不替换项目已有工具。
5. 保留用户未提交改动；遇到重叠修改时理解并协作，不重置或覆盖。

完成条件：已明确目标模块、活动规范、现有 change、工作区状态和验证入口。

## 选择流程

- 新功能、跨模块修改、API 或数据库变更：执行完整探索、change、实现、验证和归档。
- 边界清晰的中型修改：可以缩短探索，但保留 change、tasks 和验证。
- 小型文案、格式或局部低风险修复：可以不创建 change，仍需读取约束并运行适用验证。
- 难以复现的缺陷：先执行系统化调试，根因明确后再创建或更新 change。

让流程与风险匹配。既不为形式制造无价值文档，也不以“小改动”为由跳过必要验证。

## 阶段一：探索

1. 阅读相关代码、历史、契约和现有 specs。
2. 明确目标、用户场景、非目标、异常路径和兼容要求。
3. 对关键设计给出可比较方案，说明收益、成本和失败风险。
4. 识别 API、数据、安全、并发、外部依赖和运维影响。
5. 记录确认的决策和被否决方案。
6. 在缺少会显著改变行为或范围的决策时，暂停实现并请求决策。

完成条件：范围、关键行为、主要风险和必要决策可以进入 proposal/design。

## 阶段二：创建或继续 Change

先检查现有 change，继续同一目标而不是创建重复项。优先使用环境提供的 OpenSpec 能力；使用 CLI 前先运行 `openspec --help`，不要假设命令永久不变。

至少维护：

- `proposal.md`：背景、目标、非目标和影响范围。
- `design.md`：技术方案、关键决策、替代方案、迁移、风险和观测方式。
- `specs/`：可验证的行为场景。
- `tasks.md`：按依赖顺序拆分、包含验收条件的任务。

开始实现前逐项确认：

- 每项需求都有正常、边界和关键失败场景。
- API/事件状态、业务错误、幂等和兼容性已经明确。
- 数据所有权、约束、事务、迁移和并发冲突已经明确。
- 认证、授权、敏感信息、滥用和外部输入风险已经明确。
- 外部调用的 deadline、重试、容量和失败恢复已经明确。
- 日志、指标、追踪、审计和发布/回退要求已经明确。
- tasks 覆盖实现、测试、文档、迁移和验证。
- 方案遵守项目入口选中的规范和技术附录。

完成条件：design、specs 和 tasks 彼此一致，每个任务都有可检查结果。

## 阶段三：隔离工作区

遵守项目分支和 worktree 规则。大型、并行或长期变更使用独立分支/worktree；小改动可以在当前分支完成。分支名称尽量与 change name 对应。

完成条件：变更与用户现有工作隔离，基线和目标分支明确。

## 阶段四：测试驱动实现

按 tasks 依赖顺序逐项执行：

1. 读取当前 task、design 和对应 scenarios。
2. 新增或调整测试，确认测试因缺少目标行为而失败。
3. 编写使测试通过的最小实现。
4. 在测试保持通过时重构，遵守活动规范。
5. 运行当前模块适用的格式、lint、类型检查和测试。
6. 检查生成文件只由项目生成器更新。
7. 只有实现和验收条件都完成后，将 task 标记为完成。

测试覆盖正常路径、边界、关键错误、权限和并发风险。无法先写自动化测试时，在 task 中记录原因和替代验证。

完成条件：当前 task 的行为测试通过，验收证据明确，没有越界重构。

## 阶段五：系统化调试

遇到失败时：

1. 建立稳定复现，记录期望和实际结果。
2. 收集日志、调用链、输入输出、环境差异和近期变更。
3. 提出少量可证伪的根因假设。
4. 用最小实验逐个验证，不同时修改无关因素。
5. 确认根因后先补回归测试，再完成最小修复。
6. 运行相关测试和更广范围回归。

隐藏错误、无界重试和单纯扩大超时不构成根因修复。

完成条件：根因由证据支持，回归测试能在修复前后区分行为。

## 阶段六：审查与验证

先核对实现与 specs，再按以下顺序审查：

1. 正确性、安全和敏感信息。
2. API/事件契约、业务错误和兼容性。
3. 数据约束、事务、迁移和并发。
4. 外部依赖、资源上限、失败恢复和可观测性。
5. 测试有效性、设计复杂度和变更范围。
6. 项目画像、通用规范和选中技术附录的符合性。

运行仓库真实提供的格式、lint、类型、测试、构建、迁移和契约命令。OpenSpec 自身校验只证明产物结构有效，不证明实现符合设计；继续使用实现验证能力或人工逐项核对所有 scenarios 和 tasks。

声称完成前报告刚刚执行的命令、结果、跳过项和剩余风险。

完成条件：所有 scenarios 和 tasks 有实现证据，适用门禁通过，失败均已解释。

## 阶段七：归档

仅在以下条件全部满足时归档：

- tasks 全部完成。
- specs、design 与实现一致。
- 必要的测试、静态检查、构建和迁移验证通过。
- 文档、兼容和运维说明完整。
- 没有未解释的失败或高风险例外。

优先使用环境提供的 OpenSpec 归档能力；否则根据当前 `openspec --help` 执行。归档后检查主 specs 是否同步，git diff 是否只包含预期文件。

## 中断恢复

恢复工作时重新建立事实：

1. 读取项目入口、活动规范和本 Skill。
2. 查看 change 的 proposal、design、specs 和 tasks。
3. 查看分支、工作区和最近提交。
4. 从第一个未完成 task 继续，并重新运行相关验证。

## 完成输出

最终报告包含：

- 完成的行为变化。
- 主要修改模块或文件。
- 实际验证命令和结果。
- 跳过项、剩余风险或后续迁移。
- 已创建的分支、提交、推送或 PR 信息。
