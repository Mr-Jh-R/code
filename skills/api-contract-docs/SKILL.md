# API 契约与调用方文档

交付调用方能够直接使用的文档：字段准确、示例合法、版本一致、调用约束清楚。语言和文档格式沿用项目约定；缺少约定时采用用户使用的语言。通过项目入口发现文档、协议和命令，不绑定框架、平台、端口或业务文件名。

## 1. 确定范围和版本

1. 读取项目入口、Git 协作规则、相关技术规范及已有 API 文档索引。只审查时保持只读；编写或更新时优先维护现有权威文档。
2. 确认读者、模块和协议。HTTP、事件、WebSocket、RPC 与外部代理按各自契约核对，出站事件不计入本服务入站路由。
3. 用户指定工作区、分支、提交或发布版本时以其为准；否则采用项目确认的集成开发基线。记录源码 SHA、相关未提交实现、契约来源和核对日期。基线仍有歧义时先盘点差异，不能凭当前目录或固定端口认定。
4. 未集成接口可形成标明分支的开发预览，不能混写成集成版本已可用。服务器版本只在明确核对发布目标或比较部署差异时使用；普通本地文档维护无需连接服务器。
5. Base URL、认证、版本与已确认的可用状态保留在调用方文档中；构建来源和排查过程放在审查反馈或已有追溯记录中。

完成条件：文档入口、读者、版本和只读/编辑范围明确；上下文已有答案时直接继续。

## 2. 建立契约清单

- 先识别权威定义：OpenAPI、AsyncAPI、Protocol Buffers、GraphQL schema 或项目实际协议；设计中的定义与已实现行为分开记录。支持从源码生成契约时，使用项目现有导出方式。
- 在线读取契约前核对后端启动来源、构建产物和对应源码。端口监听、健康成功、localhost 或文档展示页面本身均不能证明版本一致。
- 同版本实例可直接复用。编辑文档确需启动服务时，在任务允许范围内按项目规范启动属于本任务的实例，优先使用隔离数据并停用有业务副作用的后台任务。只读核对或用户禁止启停时不启动服务。
- 无法运行时使用有生成来源、版本和时间证据的契约快照，或继续源码/测试核对并标注运行验证缺口；不静默切换到其他旧服务。快照生成后的相关代码变化也要核对。
- HTTP 接口用“方法 + 路径模板”标识；参数名可归一化用于匹配，但字段名差异仍需核对。只在已确认 Base URL 后处理上下文前缀。
- 用路由注册、协议定义和相关测试补充隐藏、条件注册或生成文档未覆盖的入口。将范围内条目归为已覆盖、缺失、过时、弃用或待确认；部署状态另记，排除项说明原因。

### 可选的 OpenAPI 机械检查

已有 OpenAPI 3.x JSON 和 Markdown 时，可运行随 Skill 分发的只读脚本；其他协议、YAML 或 Swagger 2 不适用该脚本，使用项目自己的检查工具。

```text
python -X utf8 -B <skill目录>/scripts/audit_openapi.py --openapi <定义.json> --document <文档.md>
```

需要限定模块时重复传 `--include-prefix <路径>`；只有存在已确认的上下文前缀时才传 `--base-path <前缀>`。脚本只读本地输入并向标准输出返回 JSON，不连接服务；保存结果时遵守项目临时产物规则。

结果包含路由提及情况、JSON 示例语法、重复显式锚点、宽泛响应和可疑上传定义。它不覆盖全部 OpenAPI 组合、引用和字段语义，命中路径也不等于该接口已完整说明。退出成功只表示脚本完成，仍要检查输出中的候选问题。

完成条件：范围内接口均有归属，统计口径和未确认部分清楚。

## 3. 核对真实契约

结合目标版本的定义、绑定/序列化方式、DTO、实现校验、测试和可用响应证据逐项核对：

| 类别 | 调用方需要的事实 |
| --- | --- |
| 请求 | 字段名、参数位置、类型、必填、默认值、范围、长度、数组和条件必填 |
| 响应 | 包装与嵌套结构、大小写、数组/对象/JSON 字符串、缺省与 null、单位和时间格式 |
| 行为 | 枚举、操作资格、同步/异步、部分成功、幂等、版本冲突和重试条件 |
| 查询 | 分页起点、默认/最大条数、排序、过滤和默认范围 |
| 文件与流 | Content-Type、表单字段、大小/类型、下载响应头、二进制与 JSON 错误、流终止条件 |
| 错误与权限 | 认证、授权、协议状态与业务码、触发条件及调用方动作 |

重点核对生成定义的盲区：宽泛对象、别名、自定义解析、代码中的校验、条件权限和异常转换。示例省略字段不能证明字段永远为空。

证据冲突时区分文档错误、实现缺陷、版本不同和证据不足。文档任务不自动改变接口、数据库或部署；未确认项明确标注，不伪造联调成功。

请求副作用以实现为准，不能只凭 HTTP 方法判断。优先使用既有测试和脱敏样例；为取得响应而创建、删除、导入、发消息、调用收费模型或发布，需要动作已在用户授权范围内。

完成条件：改写的每个字段和约束都有依据，示例无真实秘密或无关个人数据。

## 4. 编写文档

写 HTTP 调用文档时读取 [接口文档模板](references/frontend-api-template.md)。其他协议保留同样的输入、输出、错误和行为说明，按项目协议调整章节。

- 保持现有主文档和索引；修改契约说明时同步字段表、示例、状态和链接，避免另建“最新版”副本。
- 每个接口就近写明用途、方法/路径、入参、合法请求、成功响应、主要字段和必要错误。无请求体、无返回体或文件流需明确写出。
- 通用鉴权、响应包装与错误只定义一次；公共对象可以链接，但链接不能替代本接口主要字段和特殊约束。
- 补充会改变调用方处理方式的空结果、异步、部分失败、版本冲突等示例。JSON 代码块保持合法，节选标明范围；示例的 ID 和版本前后关联。
- 使用调用方术语解释如何调用、如何处理错误。内部 SQL、线程、算法和部署步骤留在相应技术文档中。
- 明确开发预览、已发布、弃用和兼容内容的适用范围；没有部署证据时不判断是否上线。

## 5. 验证和反馈

1. 复核接口清单、字段表和示例，检查类型、必填、大小写、枚举、时间、分页、Content-Type 和错误。
2. 运行适用的文档或契约检查，核对链接、锚点、JSON 和旧新冲突。生成客户端仅用项目规定的生成器。
3. 纯文档修改运行相关检查即可；为获取同版本定义而需要的编译或导出测试按项目约定执行。机械检查不代表写接口已联调。
4. 直接反馈新增/修改/删除了哪些文档条目及字段说明，区分已有接口补文档与代码契约变更。只读审查返回带位置和影响的差异清单，不改文件。
5. 简述实际验证、缺口以及适用的提交/集成状态。额外审查报告仅在用户要求或项目已有交付约定时生成。

完成条件：每个改动可追溯到目标版本的证据，读者无需依靠内部实现细节即可正确调用。
