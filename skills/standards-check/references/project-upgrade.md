# 已有项目的规范升级

仅在试用新版、正式升级、项目回退或已有项目基线不明确时读取。普通检查沿用已确定基线；全局安装与版本命令见 [本地版本指引](local-versions.md)。

## 先识别操作

| 用户意图 | 执行范围 | 完成条件 |
| --- | --- | --- |
| 安装/更新全局规范 | 安装指定不可变快照，保留其他版本 | 新快照通过校验；默认与项目记录保持原值 |
| 更新 Skill | 备份并合并流程文件，记录来源 SHA | 流程可用；规范快照独立保留 |
| 用新版检查一下 / 升级预检 | 临时选新版，只读比较适用差异 | 输出升级差距；项目正式版本保持原值 |
| 将这个项目升级到新版 | 预检、处理差异、验证、更新项目采用信息 | 项目记录、实际规则与必要实现一致 |
| 将新版设为全局默认 | 更新用户默认选择 | 已固定版本的项目继续使用项目版本 |

已有明确升级授权时完成授权范围内的处理，不把每一步变成确认环节。仅“检查更新”“安装新版”不授权迁移业务项目；目标项目或目标版本无法确定时先提供实际选项。

## 1. 确定旧基线与目标

- 从项目权威入口读取规范 source、版本/tag、SHA、正文位置和项目补充规则；核对实际文件，区分仅引用全局快照与已复制正文的项目。
- 对新旧快照执行完整性校验；目标 tag 对应固定 SHA。版本缺失时按已授权安装范围获取，不混用其他快照。
- 已有项目没有固定版本时，查入口、安装记录和 Git 历史。旧基线无法证实时标为“待确认”，以项目实际规则描述现状；可做新版预检，但不能把全局默认冒充旧基线或直接宣布升级完成。
- 当前任务换项目、换源码分支或项目固定版本变化时重新核对。一次新版预检的会话选择只属于该次预检，后续普通检查恢复项目正式版本，除非用户明确要求继续试用。

完成条件：明确项目当前采用信息、目标来源/tag/SHA、操作范围；无法确认的旧基线单独列出。

## 2. 预检与差异处理

读取新旧版本的 CHANGELOG 和目标技术栈章节，比较实际规则变化；Python 项目不因升级而引入 Java 附录。发现分为旧版已存在的违规、新版新增或改变的要求、项目补充/例外及不适用项。预检读取两版是为了比较，每项发现标注依据，不将两版合为一套权威规范。

- **只有版本指针**：检查新规则对代码、工具和接口兼容性的影响，再准备更新指针；没有必要复制整套正文。
- **已复制或定制正文**：三方比较“旧版原文、项目当前文件、新版原文”。未改区域采用新版，项目新增约定保留，同段冲突逐项合并；删除、移动文件先检查引用，避免留下第二个活动入口。
- 找不到旧原文时，不推测项目定制内容的归属；列出无法安全合并的具体差异。能够独立确认的部分继续处理，剩余冲突请求用户决定。
- 正式升级按授权修正适用差距并运行相关验证；已有公开 API 的兼容变化按项目迁移方案处理。允许延期的项目例外须记录适用范围、原因和复审条件，不修改全局快照以规避检查。

仅预检到这里结束，反馈采用旧版、试检新版及差距即可。正式升级的完成条件是：适用差距已修复或有项目允许的明确例外，必要检查通过，未决冲突已解决。

## 3. 固定项目版本与交付

验证通过后，在已有项目画像或工作流入口记录来源、目标 tag、完整 SHA、正文位置/读取方式、所选附录与项目例外；保留原有路径和项目事实。无需为此强制新增配置文件；全局缓存的用户绝对路径不写入共享项目记录。

同步 AGENTS/CLAUDE 等实际入口，使项目只有一套明确的活动基线。声明或解析版本不等于合规验证；只有文件和检查证据一致才报告“项目已升级”。未完成时保留旧正式版本，记录目标版本和待办，不能只改版本号。

按项目 Git 流程提交本次升级的明确文件，保留旧规范选择和必要代码调整的追溯点。反馈全局安装状态、本次检查版本、项目正式版本、验证结果、提交与发布状态；不要求另外生成长报告。

## 4. 回退

临时检查切回旧版本即可。正式项目回退需比较升级后的后续修改，同步恢复采用记录、规则副本和必要代码/配置，保留其他任务改动并重新验证。选择旧规范不会自动撤销代码或数据迁移；数据与公开契约按项目独立回退方案处理。

例如全局并存 v2.4.0/v2.5.0，项目 A 固定 v2.4.0，项目 B 固定 v2.5.0：安装或默认切换不修改 A。A 试检 v2.5.0 后仍正式采用 v2.4.0；只有完成正式升级后才更新 A 的记录。项目特有例外随项目维护，不写回共享快照。
